**기본 정보:**
- 플랫폼: 서울특별시 공공데이터 포털
- 인증 방식: 회원가입 후 인증키(API Key) 발급

## 4. 수집 전략

### 4.1 API 호출 전략

```
┌─────────────────────────────────────────────────┐
│              API 호출 기본 전략                    │
├─────────────────────────────────────────────────┤
│ 1. 페이지네이션: 1,000건 단위 순차 호출            │
│ 2. 재시도: 최대 3회, 지수 백오프 (2초→4초→8초)      │
│ 3. 타임아웃: 요청당 30초                           │
│ 4. 동시성: API별 최대 3개 동시 요청                 │
│ 5. 에러 핸들링: HTTP 4xx/5xx 분기 처리             │
└─────────────────────────────────────────────────┘
```

**서울열린데이터광장 호출 예시:**

```
GET http://openapi.seoul.go.kr:8088/{KEY}/json/{서비스명}/{시작}/{끝}

예) 추정매출 1~1000건:
GET http://openapi.seoul.go.kr:8088/{KEY}/json/VwsmTrdarSelngQq/1/1000
```

**페이지네이션 로직:**
1. 첫 요청으로 `list_total_count` (전체 건수) 확인
2. `ceil(total / 1000)` 만큼 반복 호출
3. 각 페이지: `start = (page-1)*1000 + 1`, `end = page * 1000`

### 4.2 ETL 파이프라인 구조

```
[데이터 소스]          [수집 (Extract)]        [변환 (Transform)]       [적재 (Load)]

Seoul Open Data ──→ SeoulOpenDataCollector ──→ FieldMapper ──→ PostgreSQL + PostGIS
                    │                         │                │
data.go.kr ────────→ DataGoKrCollector ───────→ Validator ────→ UPSERT (충돌 시 갱신)
                    │                         │                │
CSV Backup ────────→ CsvLoader ──────────────→ Transformer ──→ Backup Table
```

### 4.3 수집 모듈 상세

#### 4.3.1 서울열린데이터광장 수집기 (`SeoulOpenDataCollector`)

```python
# 수집 대상 API 매핑
SEOUL_API_MAP = {
    "district_polygon": "VwsmTrdarSelngW",       # OA-15560 상권영역
    "floating_pop":     "VwsmTrdarFlpopQq",      # OA-15568 유동인구
    "worker_pop":       "VwsmTrdarWrcPopltnQq",  # OA-15569 직장인구
    "resident_pop":     "VwsmTrdarPopltnQq",     # OA-15570 상주인구
    "district_change":  "VwsmTrdarStorQq",       # OA-15571 상권변화지표
    "estimated_sales":  "VwsmTrdarSelngQq",      # OA-15572 추정매출
    "store_info":       "VwsmTrdarStorW",        # OA-15577 점포정보
}
```

**처리 흐름:**
1. API Key 환경변수에서 로드 (`SEOUL_OPENDATA_API_KEY`)
2. 각 서비스에 대해 전체 건수 조회
3. 1,000건 단위 페이지네이션으로 전체 데이터 수집
4. JSON 응답 파싱 → 리스트로 변환
5. 수집 결과 로깅 (건수, 소요시간, 에러)

#### 4.3.2 공공데이터포털 수집기 (`DataGoKrCollector`)

- 소상공인 상가정보 API (`15012005`)
- 업종코드 파일데이터 (`15067631`)
- REST API 호출 or CSV 파일 다운로드

### 4.4 변환 (Transform) 규칙

#### 4.4.1 좌표 변환
- 원본: EPSG:5181 (서울시 좌표계)
- 변환 대상: EPSG:4326 (WGS84, 카카오맵/deck.gl 사용)
- 방법: PostGIS `ST_Transform(geom, 4326)` 또는 Python `pyproj` 라이브러리

#### 4.4.2 공통 변환 규칙

| 원본 | 변환 | 비고 |
|------|------|------|
| 상권_구분_코드 (TRDAR_SE_CD) | A→골목상권, D→발달상권, ... | 코드 → 한글명 매핑 |
| 성별_구분_코드 | 1→M, 2→F | D01 스펙 기준 |
| 연령대_구분_코드 | 10→10s, 20→20s, ... | D01 스펙 기준 |
| 시간대_N 컬럼 | 컬럼 → 행 변환 (unpivot) → `time_slot` + 값 | F03/F06 쿼리 편의 |
| 좌표 목록 | WKT POLYGON 변환 | PostGIS geometry |
| 기준_분기_코드 | YYYYQN 형식 | 연도+분기 통합 |

### 4.5 적재 (Load) 전략

#### 4.5.1 초기 적재 (Initial Load)
1. 전체 데이터를 수집하여 임시 테이블(`_staging`)에 적재
2. 데이터 검증 통과 후 본 테이블로 `INSERT`
3. 인덱스 생성: `(district_code, year, quarter)` 복합 인덱스

#### 4.5.2 백업 전략 (D01 스펙 연동)
- 적재 전, 기존 분기 데이터를 `_backup` 테이블에 복사 (D01 스펙 기준)
- 적재 실패 시 롤백하고 에러를 로깅 (테이블별 전체 적재 성공 시에만 COMMIT)

#### 4.5.3 증분 업데이트 (Incremental Update)
1. 최신 분기 데이터만 수집
2. `UPSERT` (INSERT ON CONFLICT UPDATE) 사용
3. 기존 데이터는 덮어쓰기 (상권 코드 + 연도 + 분기 기준)

```sql
INSERT INTO estimated_sales (district_code, year, quarter, industry_code, monthly_sales, ...)
VALUES (...)
ON CONFLICT (district_code, year, quarter, industry_code)
DO UPDATE SET
  monthly_sales = EXCLUDED.monthly_sales,
  updated_at = NOW();
```

#### 4.5.4 데이터 검증 절차

```
검증 단계:
1. Row Count 검증: 수집 건수 vs API 반환 total_count 일치 확인
2. NULL 비율 검증: 핵심 필드 NULL 비율 5% 이하
3. 범위 검증: 매출금액 >= 0, 인구수 >= 0
4. 상권코드 참조 무결성: 모든 상권코드가 districts 테이블에 존재
5. 분기 일관성: year-quarter 조합이 유효한 범위 내
```

### 4.6 스케줄링

- **주기**: 분기별 1회 (1월, 4월, 7월, 10월 첫째 주)
- **Phase 0~1**: CLI 수동 트리거 (`python -m server.data.etl.scheduler --quarter 2025Q3`)
- **Phase 2 이후**: Celery Beat + Redis Broker 자동 스케줄링으로 전환
- **실행 순서**: 상권영역 → 유동인구 → 추정매출 → 점포정보 → 인구(상주/직장) → 상권변화지표
- **완료 후**: Redis 캐시 무효화 (D01 스펙: `FLUSHDB`)
- **알림**: ETL 완료/실패 시 Slack 또는 이메일 알림
- **성능 기준**: 1개 분기 전체 ETL 30분 이내 완료 (D01 수용 기준)

### 5.3 추천 스코어링에서의 데이터 활용 (F07)

```
추천 점수 = (점포당 매출) × (연령 매칭률) × (1 - 폐업률) ÷ (경쟁 밀도)

필요 데이터:
- 점포당 매출: 추정매출(D3) ÷ 점포수(D4)
- 연령 매칭률: 유동인구 연령분포(D2) vs 업종별 주 고객 연령
- 폐업률: 점포정보(D4)의 CLSBIZ_RT
- 경쟁 밀도: 점포정보(D4)의 해당 업종 점포수
```

### 5.4 안정성 스코어 계산 (F08)

```
안정성 점수 (0~100) 계산 요소:
- 폐업률 (weight: 40%): 점포정보(D4) → 낮을수록 높은 점수
- 분기별 추이 (weight: 30%): 점포이력(D8) → 폐업률 감소 추세 시 가산
- 생존기간 (weight: 30%): 점포이력(D8) → 평균 생존기간 길수록 높은 점수
```
