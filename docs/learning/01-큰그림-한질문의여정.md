> 목적: "강남역 카페 어때?" 한 줄이 화면→서버→AI→데이터→화면으로 한 바퀴 도는 여정을 추적한다.

## §0 큰 그림

### 레스토랑 비유

손님(사용자)이 홀(브라우저)에 앉아 주문서 한 장을 내민다. "강남역 카페 어때요?"

주문서는 홀 담당(FastAPI `/api/chat`)에게 전달된다. 담당은 주문서를 읽어 손님이 어느 테이블(상권)에 앉아 있는지 확인하고, 주방장(Planner)에게 넘긴다. 주방장은 메뉴 계획(plan)을 세운다. "카페 데이터 꺼내오고, 매출 꺼내오고, 추천 돌리자." 요리사(Actor)가 창고(PostgreSQL/Redis)를 오가며 재료를 실제로 꺼내 온다. 품질 검사자(Evaluator)가 재료가 충분한지 확인한다. 부족하면 주방장에게 되돌린다. 충분하면 셰프(Respond)가 최종 요리를 만들어 홀로 올려 보낸다.

요리가 홀에 오는 방식이 특별하다. 한 접시씩 완성될 때마다 즉시 내보내는 것이다. "분석 중입니다"(thinking) → "계획 세웠어요"(plan) → "데이터 꺼냅니다"(tool) → "카드 완성"(card) → "최종 설명"(text) → "이런 것도 물어봐요"(suggestion) → "다 됐어요"(done). 손님은 마지막 요리가 나오기 전에 이미 중간중간 결과를 볼 수 있다.

이것이 MarketScope AI가 사용하는 **SSE(Server-Sent Events, 서버가 한 줄씩 밀어 보내는 스트리밍 방식)** 의 핵심이다.

### 핵심 흐름 다이어그램

```mermaid
sequenceDiagram
    autonumber
    participant 사용자
    participant 브라우저
    participant FastAPI
    participant Planner
    participant Actor
    participant Evaluator
    participant Respond
    participant DB

    사용자->>브라우저: "강남역 카페 어때?"
    브라우저->>FastAPI: POST /api/chat {message, session_id, district_code}
    Note over 브라우저,FastAPI: Next.js rewrite 미사용 — NEXT_PUBLIC_API_URL로 직접 호출

    FastAPI->>FastAPI: 세션 조회·생성 / 상권명 자동 감지
    FastAPI-->>브라우저: SSE: map_cmd (지도 이동)

    FastAPI->>Planner: run_agent() 호출 → _build_pae_graph()
    Note over FastAPI,Planner: asyncio.Queue(maxsize=256) 로 연결

    FastAPI-->>브라우저: SSE: thinking {"step": "질문 분석 중..."}

    Planner->>Planner: intent 분류 (rule-first → LLM-fallback)
    Planner->>Planner: plan 생성 [ToolPlanStep, ...]

    FastAPI-->>브라우저: SSE: plan {intent, steps[]}

    Planner->>Actor: route_after_planner → "actor"

    loop Tool 실행 (의존성 layer별 asyncio.gather)
        FastAPI-->>브라우저: SSE: tool {name, progress_label, icon}
        Actor->>DB: SQL 쿼리 (PostGIS / Redis 캐시)
        DB-->>Actor: 결과 반환
        FastAPI-->>브라우저: SSE: tool_end {name, done_label}
        FastAPI-->>브라우저: SSE: card {card_type, data}
    end

    Actor->>Evaluator: route (actor → evaluator)

    alt 데이터 부족 (최대 3라운드)
        Evaluator->>Planner: route_after_evaluator → "planner"
        FastAPI-->>브라우저: SSE: thinking {"step": "추가 데이터 수집 중..."}
    else 충분
        Evaluator->>Respond: route_after_evaluator → "respond"
    end

    Respond->>Respond: LLM 스트리밍 (Gemini pro / Claude Sonnet)

    loop 토큰 청크
        FastAPI-->>브라우저: SSE: text {content}
    end

    FastAPI-->>브라우저: SSE: suggestion {questions[]}
    FastAPI-->>브라우저: SSE: done {trace_id?}

    브라우저->>브라우저: eventHandlers.ts → store dispatch
    브라우저->>사용자: 카드·텍스트·추천 질문 렌더링
```

## §1 브라우저에서 시작 — `useChat.ts`

**비유**: 손님이 직접 주문서를 작성하고 홀 담당에게 건네는 순간.

사용자가 ChatInput에 텍스트를 입력하고 전송하면, React 컴포넌트는 `useChat` 훅의 `sendMessage` 함수를 호출한다.

```ts
// frontend/src/hooks/useChat.ts:52-56
await useChatStore.getState().sendMessage(
  message,
  selected?.code,   // 현재 지도에서 선택된 상권 코드
  onMapCmd          // map_cmd 이벤트 수신 시 지도를 움직일 콜백
);
```

`useChat`은 얇은 조율자다. 세 개의 Zustand 스토어(chatStore · districtStore · mapStore)를 묶어 하나의 `sendMessage` 인터페이스로 노출한다. 실제 HTTP 요청과 SSE 파싱은 `chatStore.sendMessage` 안에 위임된다.

**중요 설계 결정**: Next.js의 `/api/*` rewrite 프록시를 경유하지 않고 `NEXT_PUBLIC_API_URL`로 백엔드를 직접 호출한다. 이유는 Next.js 프록시가 SSE 스트림을 버퍼링해 실시간성을 해치기 때문이다. (상세: `docs/architecture/frontend.md §2`, `MEMORY.md::feedback_sse_buffering.md` 참조)

`map_cmd` 이벤트가 도착하면 `onMapCmd` 콜백이 즉시 `mapStore.setView()`와 `districtStore.select()`를 호출해 지도를 상권 위치로 이동시킨다. 이것이 "챗봇에서 상권을 언급하면 지도가 따라 움직이는" 양방향 동기화의 핵심이다.

자세한 스토어 구조와 SSE 파서는 [02 프론트엔드 화면](02-프론트엔드-화면.md)에서 다룬다.

## §2 서버 진입 — `chat.py`

**비유**: 홀 담당이 주문서를 받아 테이블 번호를 확인하고 주방에 올려 보내는 과정.

`POST /api/chat` 핸들러(`server/server/api/routes/chat.py:183`)는 요청을 받은 즉시 `EventSourceResponse`를 반환한다. 이때 실제 응답은 `event_generator()` 제너레이터가 나중에 한 줄씩 밀어 보내는 방식이다.

**핸들러가 하는 세 가지 준비 작업**:

1. **세션 복원**: `_get_session(session_id)`로 이전 대화 맥락(상권 코드·대화 이력)을 불러온다.

2. **상권 자동 감지** (district_code 없을 때): 메시지 본문에서 상권명을 추출한다.
   - `da.districts.detect_district_by_name(body.message)` — 퍼지 매칭
   - 탐지 점수 < `STRONG_TOP1_MIN(0.70)` 이면 거부 — 서울 외 지역이 엉뚱한 상권으로 매핑되는 것을 막는 두 번째 방어선
   - 탐지 실패 시 세션의 `last_district_code`로 폴백

3. **인사 단축 경로**: `_GREETING_PATTERN`이 매칭되면 Agent 파이프라인 전체를 건너뛰고 즉시 `text`·`suggestion`·`done` 세 이벤트만 반환한다(`<1s` 응답).

준비가 끝나면 `run_agent()`를 호출해 PAE 그래프를 시작하고, 그래프가 `asyncio.Queue`에 올려 보내는 이벤트를 하나씩 꺼내어 SSE로 흘려보낸다:

```python
# server/server/api/routes/chat.py:344-373 (요약)
async for event in run_agent(message=body.message, district_code=...):
    yield {"data": json.dumps(event, ensure_ascii=False, default=str)}
```

동시에 20개 이상의 채팅이 들어오면 `_chat_semaphore`가 대기를 걸고, 같은 세션에서 두 번째 요청이 오면 `_claim_session_slot`이 이전 스트림을 취소한다(지도에서 상권을 빠르게 바꿀 때 발생하는 레이스 컨디션 방어).

API 계층의 전체 엔드포인트 목록과 미들웨어 순서는 [docs/architecture/backend.md](../architecture/backend.md)를 참조한다.

## §3 AI 그래프 기동 — `graph.py`

**비유**: 주방장·요리사·품질 검사자·셰프가 한 팀을 이루어 분업하는 과정. `graph.py`는 이 팀의 조직도(그래프)를 만들고 실행한다.

`run_agent()` 함수(`server/server/agent/graph.py:248`)는 두 가지 일을 동시에 처리한다.

**① 제한된 큐(Bounded Queue)로 백프레셔 제어**:
```python
# server/server/agent/graph.py:277
event_queue: asyncio.Queue[dict | None] = asyncio.Queue(maxsize=settings.sse_queue_maxsize)
```
큐가 꽉 차면 그래프가 자연스럽게 멈춰 대기한다. SSE 소비 속도가 느린 클라이언트가 있어도 메모리가 무한 증가하지 않는다.

**② PAE 그래프 컴파일**:
```python
# server/server/agent/graph.py:305
compiled = _build_pae_graph(event_queue)
```

`_build_pae_graph`는 5개 노드(planner · greeting · clarification · actor · evaluator · respond — 실제로는 6개)와 조건부 에지(conditional edge)로 이루어진 LangGraph `StateGraph`를 만든다. 에지가 단순한 함수 호출이 아닌 이유는 Evaluator가 "데이터 부족"이라고 판단하면 Planner로 되돌아가는 루프가 존재하기 때문이다(최대 3라운드).

그래프 구조 전체는 [docs/architecture/agent.md §1](../architecture/agent.md)에 ASCII 다이어그램으로 정리되어 있다.

**이벤트가 브라우저에 도달하는 경로**:
```
그래프 노드 → event_queue.put({type: "..."}) → run_agent yield → chat.py yield → SSE
```
`graph.py`의 `_run_graph()` 코루틴(비동기 함수, `asyncio.create_task`로 백그라운드 실행)이 그래프를 돌리면서 각 단계마다 `event_queue`에 이벤트를 쌓는다. 메인 루프는 큐에서 꺼내어 `yield`로 `chat.py`에 전달하고, `chat.py`는 이것을 SSE 와이어로 흘려보낸다.

그래프 자체의 흐름(Planner가 intent를 분류하는 방법, Actor가 Tool을 병렬 실행하는 방법, Evaluator가 충분성을 판단하는 방법)은 각각 [04 AI 에이전트: 분석팀](04-AI에이전트-분석팀.md)에서 줄별로 해설한다.

## §4 각 단계에서 브라우저가 받는 것

| 단계 | SSE 이벤트 | 브라우저 동작 |
|------|------------|--------------|
| 서버 진입 후 상권 확정 | `map_cmd` | 지도가 강남역으로 이동 |
| `run_agent()` 최초 호출 | `thinking` | "질문 분석 중..." 로딩 표시 |
| Planner 완료 | `plan` | 계획 단계 표시 |
| Actor: Tool 시작 | `tool` | 도구 이름 + 진행 표시 |
| Actor: Tool 완료 | `tool_end` | 완료 아이콘 |
| Actor: 카드 발행 | `card` | SummaryCard / RecommendCard 등 렌더링 |
| Evaluator: 부족 판정 | `thinking` | "추가 데이터 수집 중..." |
| Respond: 토큰 스트리밍 | `text` | 글자가 하나씩 나타남 |
| 스트림 종료 직전 | `suggestion` | "이런 것도 물어봐요" 칩 표시 |
| 완료 | `done` | 로딩 표시 해제, Langfuse trace_id 로그 |

브라우저에서 이 이벤트들을 처리하는 파서와 핸들러는 `frontend/src/lib/sseParser.ts`와 `frontend/src/lib/eventHandlers.ts`다. 자세한 내용은 [02 프론트엔드 화면](02-프론트엔드-화면.md) 참조.

## §5 단축 경로 — 그래프를 건너뛰는 두 가지 경우

풀 PAE 파이프라인은 Tool 실행 + LLM 3회(Planner·Evaluator·Respond)를 거치므로 약 5~15초가 걸린다. 다음 두 경우는 그래프 자체를 건너뛴다.

**① 인사 단축**: `chat.py`의 `_GREETING_PATTERN`이 "안녕", "hi" 등을 감지하면 `run_agent()`를 호출하지 않고 즉시 3개 이벤트(`text`·`suggestion`·`done`)만 반환한다. 응답 시간 < 1초.

**② Greeting/Clarification 노드**: 메시지가 인사를 통과했더라도 Planner가 `response_mode="greeting_direct"` 또는 `"clarification_direct"`를 반환하면, 그래프 내에서 `greeting` 또는 `clarification` 노드로 라우팅되어 바로 `END`로 빠져나온다. Actor·Evaluator·Respond를 거치지 않는다.

이런 단축 경로는 서울 외 지역 질문(예: "부산 해운대 알려줘")도 처리한다. Planner의 `intents.yaml`에 `out_of_scope` intent가 정의되어 있어 LLM·Tool 호출 없이 즉시 거절 메시지를 반환한다.

## §6 이 문서가 가르치는 핵심 원칙

1. **SSE 직접 호출**: Chat 스트림은 Next.js 프록시를 우회하고 `NEXT_PUBLIC_API_URL`로 직접 백엔드를 호출한다. 프록시 버퍼링이 실시간성을 망가뜨리기 때문이다.

2. **SSE 9 이벤트의 순서**: `map_cmd` → `thinking` → `plan` → `tool`/`tool_end`/`card` (반복) → `thinking`(재라운드 시) → `text` (스트리밍) → `suggestion` → `done`. 이 순서가 사용자가 보는 점진적 로딩 경험을 만든다.

3. **PAE 루프의 목적**: Planner가 계획을 세우고 → Actor가 실행하고 → Evaluator가 결과를 검증한다. 검증 실패 시 Planner로 되돌아가 최대 3라운드를 반복한다. 이는 단순 ReAct(도구 호출-관찰-반복) 패턴보다 계획·실행·검증의 책임이 명확하게 분리된 구조다.

4. **asyncio.Queue 백프레셔**: 이벤트 큐 크기는 256으로 제한(`sse_queue_maxsize`)된다. 느린 클라이언트 때문에 서버 메모리가 늘어나지 않도록 자연스럽게 생산자를 제어한다.

5. **세션 격리와 레이스 방어**: 같은 `session_id`에서 두 번째 요청이 오면 첫 번째 스트림이 취소된다(`_claim_session_slot`). 사용자가 지도에서 상권을 빠르게 바꿀 때 두 AI 응답이 뒤섞이는 문제를 막는다.

6. **단축 경로 우선**: 인사·서울 외 지역 등 LLM이 필요 없는 케이스는 그래프 진입 전(`_GREETING_PATTERN`) 또는 그래프 초입(`greeting`/`clarification` 노드)에서 빠르게 처리한다. 비용과 지연을 동시에 줄이는 설계다.

7. **LLM 역할 분리**: Planner는 Claude Sonnet 4(tool_use 정확도 우선), Evaluator는 Gemini Flash(저비용), Respond는 Gemini Pro(한국어 스트리밍 품질). 역할별로 다른 모델을 쓰는 이유는 [agent.md §6](../architecture/agent.md)를 참조한다.
