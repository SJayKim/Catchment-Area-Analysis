## 1. 프로젝트 개요

### 1-1. 문제 정의

현재 상권분석 시장의 고질적 문제:

| 문제 | 상세 |
|------|------|
| **정보 파편화** | 유동인구, 매출, 임대료, 경쟁업체 데이터가 각각 다른 플랫폼에 흩어져 있음 |
| **분석의 피상성** | 기존 서비스들은 통계 수치 나열에 그침 — "그래서 여기서 장사하면 되나요?"에 답을 못함 |
| **전문성 장벽** | 상권분석 보고서를 제대로 해석하려면 부동산·마케팅·재무 복합 지식이 필요 |
| **시의성 부족** | 공공데이터 기반 분석은 6개월~1년 전 데이터로 판단하게 됨 |
| **환각 위험** | 단일 LLM이 상권을 분석하면 실제 데이터 없이 그럴듯한 거짓을 생성 |

### 1-2. 솔루션 개요

**MarketScope AI**는 여러 전문 AI 에이전트가 팀으로 협업하여 특정 위치의 상권을 분석하고, 업종별 창업 적합도를 판단하며, 실행 가능한 전략을 제시하는 시스템입니다.

**핵심 차별점:**
- 단일 AI가 아닌 **에이전트 군집(Agent Swarm)**이 각 전문 영역을 분석
- 다중 LLM의 **교차 검증(Debate)**으로 환각 제거
- **실시간 데이터 + 공공데이터** 결합으로 시의성 확보
- 과거 분석 이력을 학습하는 **메모리 시스템**으로 점진적 품질 향상

### 1-3. 타겟 사용자

| 사용자 유형 | 니즈 | 핵심 기능 |
|-------------|------|-----------|
| **예비 창업자** | "이 자리에서 카페 열면 될까?" | 업종-입지 적합도 분석, 예상 매출 시뮬레이션 |
| **프랜차이즈 본사** | "신규 가맹점 입지를 100곳 중 10곳으로 추려줘" | 대량 입지 스크리닝, 상권 비교 랭킹 |
| **부동산 투자자** | "이 상가 건물, 공실률 올라갈까?" | 상권 트렌드 예측, 리스크 스코어링 |
| **기존 자영업자** | "우리 가게 매출이 왜 떨어지지?" | 경쟁 환경 변화 감지, 대응 전략 제안 |
| **지자체/공공기관** | "전통시장 활성화 정책 효과를 측정해줘" | 정책 효과 분석, 상권 건강도 모니터링 |

## 3. 에이전트 군집 상세 설계

### 3-1. Commander Agent (사령관)

| 항목 | 상세 |
|------|------|
| **역할** | 사용자 요청 분석, 분석 계획 수립, 에이전트 할당, 최종 품질 검증 |
| **LLM** | Claude Opus 4.6 (복잡한 추론 & 계획 수립) |
| **입력** | 사용자 자연어 쿼리, 사용자 프로필 (PersonalMemory) |
| **출력** | 분석 계획 (DAG), 에이전트 할당 명세, 최종 승인/반려 |
| **특이사항** | 가장 비싼 모델이므로 호출 최소화 — 계획 수립 1회 + 최종 검증 1회 |

**의사결정 흐름:**

```
사용자: "강남역 근처에서 퓨전 한식당 열면 어떨까요?"
                    ↓
Commander 분석:
  - 의도: 특정 위치 + 특정 업종의 창업 적합도 분석
  - 필요 에이전트: 인구, 매출, 경쟁, 입지, 재무, 트렌드
  - 병렬 실행 가능: [인구, 경쟁, 트렌드] → 순차: [매출(인구 결과 필요)] → [재무] → [입지 종합]
  - 교차 검증 필요: 매출 추정치, 입지 적합도
                    ↓
실행 계획 (DAG) 생성 → LangGraph로 전달
```

### 3-2. 전문 에이전트 (Specialist Agents) 상세

#### 인구분석 Agent (Population Analyst)

| 항목 | 상세 |
|------|------|
| **역할** | 상권 내 유동인구·거주인구·직장인구의 규모, 패턴, 트렌드 분석 |
| **LLM** | Gemini 2.5 Flash (빠른 데이터 해석) |
| **도구(MCP)** | 공공데이터 MCP (소상공인진흥공단 상권정보, 통계청 인구데이터) |
| **입력** | 위치 좌표/주소, 반경(500m/1km), 분석 기간 |

**데이터 소스 상세 매핑:**

| 데이터 | 소스 | API/데이터셋 ID | 갱신 주기 | 비고 |
|--------|------|-----------------|----------|------|
| 유동인구 (시간대/요일/성별/연령) | 소상공인진흥공단 상권정보 | `data.go.kr #15012005` (OpenAPI) | 분기별 | 상권코드 기반 조회, 핵심 데이터 |
| 서울 생활인구 | 서울 열린데이터광장 | `data.seoul.go.kr` 서울생활인구 (내국인/외국인) | 월별 | 서울 한정, 행정동 단위 시간대별 인구 |
| 주민등록 거주인구 | 통계청 KOSIS | `kosis.kr` 주민등록인구통계 | 월별 | 행정동 단위 연령/성별 |
| 직장인구 (사업체종사자) | 통계청 | `data.go.kr #15083827` 전국사업체조사 | 연별 | 행정동×업종별 종사자 수 |
| 아파트 세대수 | 국토교통부 | 공동주택단지 목록 API | 수시 | 반경 내 거주 수요 추정용 |

**데이터 Gap & 대응:**
- 서울 외 지역의 유동인구 데이터가 부족함 → **KT/SKT 통신 기반 유동인구 데이터** 유료 구매를 Phase 2에서 검토 필요
- 소상공인진흥공단 데이터는 분기 지연이 있어 **실시간성이 낮음** → 카카오/네이버 플레이스의 "현재 혼잡도" 데이터로 보완 가능

**출력 스키마:**

```
PopulationAnalysis {
    total_floating_population: int          # 일평균 유동인구
    floating_by_time: Dict[str, int]        # 시간대별 유동인구 {09시: 1200, ...}
    floating_by_day: Dict[str, int]         # 요일별 유동인구
    resident_population: int                # 반경 내 거주인구
    worker_population: int                  # 반경 내 직장인구
    age_distribution: Dict[str, float]      # 연령대별 비율

### 6-2. Debate 트리거 조건

모든 분석에 Debate를 돌리면 비용이 과다하므로 **선택적 트리거**:

| 조건 | Debate 여부 | 이유 |
|------|------------|------|
| 에이전트 간 결론 충돌 | **필수** | 인구는 유망이라는데 경쟁은 포화라고 할 때 |
| 신뢰도 점수 < 0.6 | **필수** | 데이터 부족이나 이상 패턴 감지 시 |
| 예상 매출 변동 범위 > 50% | **필수** | 불확실성이 클 때 |
| 모든 에이전트 결론 일치 | 스킵 가능 | 불필요한 Debate 비용 절감 |
| 사용자 명시적 요청 | **필수** | "좀 더 꼼꼼히 봐줘" |

### 6-3. LLM 모델 배치 전략

| 역할 | 모델 | 선택 이유 | 호출 빈도 |
|------|------|----------|----------|
| Commander / Judge | Claude Opus 4.6 | 최고 추론 능력, 복잡한 판단 | 분석당 2회 (계획+판정) |
| Critic, 입지, 재무, 리스크, 규제, 내러티브 | Claude Sonnet 4.6 | 비판적 사고, 정밀 계산, 한국어 품질 | 분석당 3~6회 |
| Advocate, 데이터 해석, 시각화 | Gemini 2.5 Flash/Pro | 빠른 속도, 대량 데이터 처리, 웹 검색 | 분석당 5~8회 |
| 임베딩 | bge-m3 (다국어) | 한국어 상권 용어 임베딩 품질 | 상시 |

**예상 비용 (분석 1건당):**

Advocate (Gemini) ×3: ~$0.015
Specialist ×8:      ~$0.12
────────────────────────────────────
총 예상: ~$0.40~0.60 / 분석 1건
```

      ├──dominant_industry──→ [카페 > 음식점 > 주점 > 미용]
      │
      ├──neighboring──→ [신논현 상권] ──competing_with──→ [강남역 상권]
      │
      ├──development_plan──→ [영동대로 지하공간 개발 2027]
      │

→ "강남역 인근" 쿼리 시 연관 상권, 리스크, 개발 계획이 함께 검색됨

## 8. LightRAG 활용법 상세

### 8-1. LightRAG가 이 프로젝트에서 해결하는 문제

```
문제: 에이전트들이 분석할 때 "정형 데이터(숫자)"만으로는 부족한 컨텍스트가 있음

예시:
- "강남역 상권은 최근 젠트리피케이션 우려가 있다" → 뉴스에서만 나오는 정보

이런 비정형 지식을 LightRAG의 Knowledge Graph로 구조화하여
에이전트가 분석 시 자동으로 관련 컨텍스트를 검색하게 함
```

### 8-4. 에이전트의 LightRAG 검색 (Query)

```python
# backend/agents/specialists/population.py — 예시

async def analyze_population(rag: LightRAG, location: str, industry: str):
    """인구분석 에이전트가 LightRAG를 활용하는 방식"""

    # ────────────────────────────────────────────
    # 검색 모드별 활용
    # ────────────────────────────────────────────

    # 1. naive 모드 — 단순 벡터 유사도 검색 (가장 빠름)
    # 용도: 특정 상권의 기본 정보 빠르게 조회
    basic_info = await rag.aquery(
        f"{location} 상권 유동인구 특성",
        param=QueryParam(mode="naive")
    )

    # 2. local 모드 — 엔티티 중심 검색 (관계 1홉)
    # 용도: 특정 상권의 직접 연결된 정보 (인접 상권, 주요 시설 등)
    local_context = await rag.aquery(
        f"{location} 상권의 인접 경쟁 상권과 주요 집객 시설",
        param=QueryParam(mode="local")
    )

    # 3. global 모드 — 전체 그래프 탐색 (가장 포괄적)
    # 용도: 업종 전체 트렌드, 규제 동향 등 넓은 범위
    global_trend = await rag.aquery(
        f"{industry} 업종의 전국적 트렌드와 리스크 요인",
        param=QueryParam(mode="global")
    )

    # 4. hybrid 모드 — local + global 결합 (가장 권장)
    # 용도: 특정 상권 + 업종의 종합적 컨텍스트
    comprehensive = await rag.aquery(
        f"{location}에서 {industry} 창업 시 고려해야 할 "
        f"인구 특성, 트렌드, 리스크 요인",
        param=QueryParam(mode="hybrid")
    )

    return {
        "basic_info": basic_info,
        "local_context": local_context,
        "global_trend": global_trend,
        "comprehensive": comprehensive,
    }
```

### 8-6. LightRAG 운영 고려사항

```
1. 데이터 갱신 전략:
   ─────────────────
   - 상권 프로필: 분기 1회 전체 재적재 (delete + insert)
   - 뉴스/트렌드: 주 1회 incremental insert
   - 법령: 변경 시에만 업데이트
   - 분석 교훈: 분석 완료 후 즉시 insert

2. 스토리지 선택:
   ─────────────────
   - Phase 1 (MVP): NetworkXStorage (파일 기반, 단일 인스턴스)
   - Phase 2+: Neo4jStorage (다중 인스턴스, 확장성)
   - 벡터 스토어: ChromaDB (ReMe와 통일)

3. 성능 최적화:
   ─────────────────
   - 검색 결과 캐싱: 동일 상권+업종 쿼리는 Redis에 24h 캐시
   - 청크 사이즈: 1200 토큰 (상권 데이터 특성상 문단 단위가 적절)
   - 임베딩 배치: 대량 적재 시 batch insert로 임베딩 호출 최소화

4. 한국어 특수 고려:
   ─────────────────
   - bge-m3 임베딩 모델 사용 (한/영 다국어 지원, 1024dim)
   - 엔티티 추출 시 한국어 고유명사(상권명, 행정동명) 인식률 확인 필요
   - LLM의 엔티티 추출 프롬프트에 "Korean" 언어 설정 필수

### 9-2. MCP 호출 흐름

```
에이전트 → MCP Client (표준 프로토콜)
              ↓
       MCP Server (Tool 실행)
              ↓
       외부 API / DB 호출
              ↓
       응답 정규화 → JSON Schema
              ↓
       에이전트에 반환
```

MCP의 이점:
- 에이전트가 데이터 소스의 구현 세부사항을 모름 (추상화)
- API 키 관리, Rate Limiting, 캐싱이 MCP 서버에서 통합 관리
- 새 데이터 소스 추가 시 에이전트 코드 변경 불필요
- 도구 목록이 자동으로 LLM에 노출 (Tool Discovery)

### 11-2. 프레임워크 상세 비교 & 선택 이유

#### 오케스트레이션: LangGraph vs CrewAI vs AutoGen

| 항목 | LangGraph | CrewAI | AutoGen |
|------|-----------|--------|---------|
| **아키텍처** | DAG 기반 그래프 | 역할 기반 에이전트 팀 | 대화 기반 멀티에이전트 |
| **상태 관리** | TypedDict State (강력) | 내부 관리 (제한적) | 메시지 기반 |
| **병렬 실행** | 네이티브 지원 (fan-out) | 제한적 | 제한적 |
| **체크포인팅** | 내장 (SQLite/PostgreSQL) | 없음 | 없음 |
| **조건 분기** | 유연 (conditional_edge) | 제한적 | 코드 기반 |
| **커스텀 도구** | 완전 지원 | 지원 | 지원 |
| **LLM 독립성** | LiteLLM 통합 용이 | LangChain 의존 | OpenAI 중심 |
| **학습 곡선** | 중간~높음 | 낮음 | 중간 |
| **프로덕션 성숙도** | 높음 (LangChain 팀) | 중간 | 중간 |

**선택: LangGraph**
- 이유: 에이전트 간 의존성(매출→재무), 병렬 실행(인구∥경쟁∥트렌드), 조건 분기(Debate 트리거)를 DAG로 명확하게 표현 가능
- 기존 side 프로젝트에서 LangGraph 사용 경험 활용

#### LLM 라우팅: LiteLLM vs LangChain Chat Models

| 항목 | LiteLLM | LangChain Chat Models |
|------|---------|----------------------|
| **지원 모델** | 100+ (거의 모든 LLM) | 주요 모델만 |
| **통합 인터페이스** | OpenAI 호환 단일 API | 모델별 래퍼 클래스 |
| **프록시 서버** | 내장 (독립 서비스) | 없음 |
| **비용 추적** | 내장 콜백 | Langfuse 연동 필요 |
| **폴백/로드밸런싱** | 내장 | 직접 구현 |
| **스트리밍** | 지원 | 지원 |

**선택: LiteLLM**
- 이유: Commander(Opus), Specialist(Gemini Flash), Critic(Sonnet) 등 모델이 다양하므로 단일 인터페이스가 필수
- LiteLLM 프록시를 Docker 컨테이너로 띄우면 API 키 관리도 중앙화

#### Knowledge Graph: LightRAG vs GraphRAG(MS) vs LlamaIndex KG

| 항목 | LightRAG | GraphRAG (MS) | LlamaIndex KG |
|------|----------|---------------|---------------|
| **그래프+벡터 통합** | 네이티브 | 그래프 중심 | 벡터 중심 |
| **검색 모드** | naive/local/global/hybrid | local/global | vector/kg |
| **설치 복잡도** | pip install 1줄 | 복잡 (Neo4j 필수) | 중간 |
| **LLM 비용** | 낮음 (경량 추출) | 높음 (커뮤니티 감지) | 중간 |
| **한국어** | bge-m3 설정 가능 | 제한적 | 설정 가능 |
| **증분 업데이트** | 지원 | 전체 재빌드 | 지원 |
| **GitHub Stars** | 28K+ | 24K+ | 38K+ |

**선택: LightRAG**
- 이유: 기존 side 프로젝트에서 사용 중, 가볍고 빠른 설치, hybrid 검색 모드가 상권분석에 적합
- 상권 데이터는 규모가 크지 않아 (전국 ~3,000개 상권) NetworkX로도 충분

  총 원가: ~$0.65 (≈ 910원)

무료 티어: 3회 × 910원 = 2,730원/월 (마케팅 비용으로 간주)
Starter (20회): 원가 18,200원 → 매출 29,000원 → 마진 37%
Pro (50회 가정): 원가 45,500원 → 매출 99,000원 → 마진 54%
```

## 15. 리스크 분석 & 완화 전략

### 15-1. 기술 리스크

| 리스크 | 영향도 | 완화 전략 |
|--------|--------|----------|
| **LLM 환각으로 잘못된 분석** | 높음 | 멀티 LLM Debate 필수, 수치는 반드시 데이터 소스 인용, 신뢰도 점수 노출 |
| **공공데이터 API 중단/변경** | 중간 | MCP 추상화 레이어로 소스 교체 용이, 데이터 캐싱, 폴백 데이터 확보 |
| **LLM 비용 예상 초과** | 중간 | 캐시 적극 활용, Debate 선택적 트리거, Flash 모델 우선 사용 |
| **분석 지연 (사용자 이탈)** | 중간 | 병렬 에이전트 실행, 점진적 결과 스트리밍, 빠른 요약 먼저 제공 |
| **에이전트 간 결과 충돌** | 낮음 | Debate 시스템이 구조적으로 해결, 최악의 경우 "판단 불가" 명시 |

### 15-2. 비즈니스 리스크

| 리스크 | 영향도 | 완화 전략 |
|--------|--------|----------|
| **기존 서비스와의 차별화 실패** | 높음 | "대화형 AI 분석"이 핵심 — 기존 대시보드형 서비스와 UX 차별화 |
| **분석 결과에 대한 법적 책임** | 중간 | "투자 조언이 아닌 참고 자료" 면책 조항, 신뢰도 점수 항상 표시 |
| **사용자 데이터 프라이버시** | 중간 | 최소 수집 원칙, 분석 히스토리 삭제 기능, GDPR/PIPA 준수 |

### 15-3. 운영 리스크

| 리스크 | 영향도 | 완화 전략 |
|--------|--------|----------|
| **1인 CTO의 병목** | 높음 | AI 에이전트가 코드 리뷰/테스트/배포 자동화, CTO는 의사결정만 |
| **LLM 모델 업데이트로 동작 변경** | 중간 | 모델 버전 고정, 업그레이드 전 회귀 테스트, A/B 테스트 |
| **외부 API 비용 증가** | 낮음 | 공공데이터 중심 (무료), 유료 API는 캐싱으로 호출 최소화 |
