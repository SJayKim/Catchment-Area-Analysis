# Plan: Playwright MCP 브라우저 기반 종합 E2E QA

## Context

Real 모드 전환 완료 (1,650개 상권 폴리곤 + 유동인구/매출/점포 데이터). 이제 **실제 사용자 관점**에서 Playwright MCP 브라우저를 열고 모든 기능을 직접 테스트한다. 각 시나리오는 독립 subagent가 수행하여 세션 격리 + 병렬 실행.

**전제**: 백엔드(Real, :8002) + 프론트엔드(:3000) + Docker(DB, Redis) 실행 중

---

## 실행 구조

```
메인 Agent
  ├─ subagent A: 시나리오 그룹 1 (지도/폴리곤/검색)
  ├─ subagent B: 시나리오 그룹 2 (채팅/Card/답변품질)
  └─ subagent C: 시나리오 그룹 3 (UX/에러/개선점 발굴)
```

각 subagent는:
1. Playwright MCP로 `http://localhost:3000` 접속
2. 시나리오 수행 → 스크린샷 캡처
3. PASS/FAIL + 상세 내용 반환
4. FAIL 시 원인 분석 포함

메인 Agent가 결과 취합 → FAIL 항목 수정 → 재테스트

## 시나리오 그룹 1: 지도 + 폴리곤 + 검색

### T1.1 첫 화면 폴리곤 렌더링
- 접속 → 3초 대기
- 스크린샷 촬영
- **PASS**: 불규칙 다각형 폴리곤 다수 표시, StatusBar에 "2025년 4분기"

### T1.2 폴리곤 클릭 → SummaryCard 데이터 검증
- 지도에서 아무 폴리곤 클릭 (snapshot에서 polygon 영역 좌표 클릭)
- 15초 대기
- **PASS 조건**:
  - StatusBar에 상권명 표시
  - SummaryCard 렌더링
  - dataQuarter = "2025Q4" ("샘플" 없음)
  - 유동인구 > 0 (일 평균 0명이 아닐 것)
  - byHour 차트에 6개 시간대 막대
  - Top 5 업종에 점포 수 > 0
  - 폐업률 숫자 표시

### T1.3 검색 "명동" → 지도 이동 + 자동 분석
- Toolbar 검색바에 "명동" 입력
- 드롭다운 결과 대기 → 클릭
- **PASS**: StatusBar에 "명동" 포함, 지도 이동, SummaryCard 자동 트리거

### T1.4 검색 "홍대" → 지도 이동
- 검색바에 "홍대" 입력
- 결과 클릭
- **PASS**: StatusBar 변경, 지도 위치 변경

### T1.5 존재하지 않는 상권 검색
- 검색바에 "뉴욕" 입력
- **PASS**: 빈 결과 또는 "검색 결과 없음" (앱 크래시 없음)

### T1.6 뷰포트 이동 시 폴리곤 동적 로드
- 지도를 강남 쪽으로 팬 이동
- 새 polygon API 호출 발생 확인
- **PASS**: 새로운 폴리곤 로드됨

## 시나리오 그룹 2: 채팅 + Card 렌더링 + 답변 품질

### T2.1 자연어 상권 분석 — "강남역 상권 분석해줘"
- 폴리곤 미클릭 상태에서 채팅 입력
- **PASS 조건**:
  - 지도가 강남역으로 이동
  - SummaryCard 렌더링 (유동인구 > 0, 매출 > 0)
  - AI 텍스트 응답에 실제 수치 언급
  - Agent progress indicator 표시됨

### T2.2 상권 비교 — "홍대입구랑 비교해줘"
- T2.1 이후 (강남역 컨텍스트 유지)
- **PASS 조건**:
  - CompareCard 렌더링 (2개 상권)
  - 유동인구/점포수/매출/폐업률 각각 다른 수치
  - "#1 ▲" 우승 표시
  - AI가 비교 분석 텍스트 작성

### T2.3 업종 추천 — "여기서 뭐하면 좋을까?"
- **PASS 조건**:
  - RecommendCard 렌더링 (Top 5)
  - 각 업종에 점수(0-100) + 근거 텍스트
  - 면책 안내 "추정치이며 실제와 다를 수 있습니다"

### T2.4 리스크 분석 — "이 자리 위험해?"
- **PASS 조건**:
  - RiskCard 렌더링
  - 위험 업종 목록 + 폐업률 %
  - 분기별 개폐업 추이 차트

### T2.5 업종 특정 분석 — "카페 하면 어때?"
- 상권 선택 상태에서 입력
- **PASS 조건**:
  - 카페/커피 관련 매출, 점포 수 데이터 포함 응답
  - 경쟁 밀집도 또는 포화도 언급
  - 텍스트 응답 (Card가 아닌 상세 분석)

### T2.6 후속 질문 — 컨텍스트 유지
- "유동인구 자세히 알려줘" (상권 미명시)
- **PASS**: 이전에 선택한 상권의 유동인구 상세 (시간대/성별/연령별)

### T2.7 다른 상권 전환 — "명동은 어때?"
- 기존 컨텍스트에서 다른 상권으로 전환
- **PASS**:
  - 지도가 명동으로 이동
  - SummaryCard가 명동 데이터
  - StatusBar 업데이트

### T2.8 답변 품질 — 데이터 일관성
- SummaryCard의 유동인구 수치와 AI 텍스트의 수치가 일치하는지
- CompareCard의 수치와 AI 비교 텍스트가 일관되는지
- **PASS**: Card 수치 = 텍스트 수치 (같은 데이터 소스)

### T2.9 답변 품질 — 면책/출처 표시
- 모든 분석 응답에 데이터 기준 분기 언급 여부
- 추천/리스크 응답에 면책 안내 포함 여부
- **PASS**: 매출 분석에 "카드 매출 기반" 또는 "추정치" 언급

### T2.10 Suggestion Chip 클릭
- 응답 후 표시되는 추천 질문 버튼 클릭
- **PASS**: 새 질의 전송 → 정상 응답

## 시나리오 그룹 3: UX + 에러 + 사용자 관점 개선

### T3.1 빈 메시지 전송
- 입력 없이 Enter
- **PASS**: 아무 일도 안 일어남 (오류 없음)

### T3.2 로딩 중 중복 전송
- 메시지 전송 후 로딩 중 다시 Enter
- **PASS**: 중복 전송 방지 (textarea disabled)

### T3.3 긴 응답 중 스크롤
- 긴 분석 응답 수신 중 채팅 패널 자동 스크롤 여부
- **PASS**: 최신 메시지가 보이도록 자동 스크롤

### T3.4 연속 상권 전환
- "강남역" → "홍대" → "건대" 빠르게 연속 전환
- **PASS**: 각각 지도 이동 + 응답 정상 (크래시/행 없음)

### T3.5 에러 복원
- 존재하지 않는 상권코드로 분석 요청 시도
- **PASS**: 친화적 에러 메시지 (백지 화면 아님)

### T3.6 SSE 스트리밍 체감
- 응답 시작까지 걸리는 시간 체감 측정
- **PASS**: 첫 thinking 이벤트 3초 이내

### T3.7 다크 테마 시각 품질
- 스크린샷으로 다크 테마 렌더링 확인
- Card 텍스트 가독성, 차트 색상 구분
- **PASS**: 텍스트 잘 읽힘, 차트 구분 가능

### T3.8 사용자 관점 — 자연어 변형 테스트
- "강남역 장사 잘 되나?" (비표준 표현)
- "여기 카페 많아?" (구어체)
- "이 동네 어떤 사람들이 다녀?" (유동인구 우회 표현)
- **PASS/FAIL + 기록**: Agent가 의도를 파악하고 적절한 Tool 호출하는지

### T3.9 사용자 관점 — 없는 기능 발굴
아래 질문들을 시도하고 응답 품질 평가 + 개선 아이디어 기록:
- "이 상권 임대료가 어때?" (임대료 데이터 없음)
- "근처 주차장 있어?" (POI 데이터 없음)
- "올해 매출 추세가 어떻게 돼?" (시계열 추이)
- "가장 잘 되는 상권 추천해줘" (상권 간 랭킹)
- "반경 500m 안에 카페가 몇 개야?" (공간 쿼리)
- "주말에 사람 많아?" (요일별 분석)
- "야간 장사하기 좋은 곳은?" (시간대 필터)
- **기록**: 각 질문에 대해 [응답 가능/불가능], [답변 품질], [개선 아이디어]

## 판정 기준

| 등급 | 기준 |
|------|------|
| **PASS** | 기대 동작 정상 수행, 데이터 정확 |
| **SOFT FAIL** | 동작하지만 품질 미흡 (답변 부정확, UX 어색) |
| **HARD FAIL** | 크래시, 빈 화면, 응답 없음, 오류 메시지 |

---

## FAIL 시 대응

```
HARD FAIL → 즉시 코드 수정 → 해당 시나리오 재테스트
SOFT FAIL → 개선 아이디어로 기록 (docs/status/improvement-ideas.md)
3회 연속 동일 FAIL → 근본 원인 재분석
```

## 실행 순서

```
1. 서비스 상태 확인 (백엔드 Real :8002 + 프론트 :3000 + Docker)
2. subagent A 실행: T1.1~T1.6 (지도/폴리곤/검색) — 스크린샷 포함
3. subagent B 실행: T2.1~T2.10 (채팅/Card/답변품질) — 순차 (대화 흐름)
4. subagent C 실행: T3.1~T3.9 (UX/에러/개선점) — 스크린샷 포함
5. 결과 취합 → HARD FAIL 수정 → 재테스트
6. 최종 리포트: docs/status/e2e-qa-report.md
   - 전체 PASS/FAIL 표
   - 스크린샷 참조
   - 개선 아이디어 목록
```
