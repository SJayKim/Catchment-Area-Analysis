## 1. 프로젝트 개요

### 1-1. 문제 정의

현재 상권분석 시장의 고질적 문제:

| 문제 | 상세 |
|------|------|
| **정보 파편화** | 유동인구, 매출, 임대료, 경쟁업체 데이터가 각각 다른 플랫폼에 흩어져 있음 |
| **분석의 피상성** | 기존 서비스들은 통계 수치 나열에 그침 — "그래서 여기서 장사하면 되나요?"에 답을 못함 |
| **전문성 장벽** | 상권분석 보고서를 제대로 해석하려면 부동산·마케팅·재무 복합 지식이 필요 |
| **시의성 부족** | 공공데이터 기반 분석은 6개월~1년 전 데이터로 판단하게 됨 |
| **환각 위험** | 단일 LLM이 상권을 분석하면 실제 데이터 없이 그럴듯한 거짓을 생성 |

### 1-2. 솔루션 개요

**MarketScope AI**는 여러 전문 AI 에이전트가 팀으로 협업하여 특정 위치의 상권을 분석하고, 업종별 창업 적합도를 판단하며, 실행 가능한 전략을 제시하는 시스템입니다.

**핵심 차별점:**
- 단일 AI가 아닌 **에이전트 군집(Agent Swarm)**이 각 전문 영역을 분석
- 다중 LLM의 **교차 검증(Debate)**으로 환각 제거
- **실시간 데이터 + 공공데이터** 결합으로 시의성 확보
- 과거 분석 이력을 학습하는 **메모리 시스템**으로 점진적 품질 향상

### 1-3. 타겟 사용자

| 사용자 유형 | 니즈 | 핵심 기능 |
|-------------|------|-----------|
| **예비 창업자** | "이 자리에서 카페 열면 될까?" | 업종-입지 적합도 분석, 예상 매출 시뮬레이션 |
| **프랜차이즈 본사** | "신규 가맹점 입지를 100곳 중 10곳으로 추려줘" | 대량 입지 스크리닝, 상권 비교 랭킹 |
| **부동산 투자자** | "이 상가 건물, 공실률 올라갈까?" | 상권 트렌드 예측, 리스크 스코어링 |
| **기존 자영업자** | "우리 가게 매출이 왜 떨어지지?" | 경쟁 환경 변화 감지, 대응 전략 제안 |
| **지자체/공공기관** | "전통시장 활성화 정책 효과를 측정해줘" | 정책 효과 분석, 상권 건강도 모니터링 |

## 3. 에이전트 군집 상세 설계

### 3-1. Commander Agent (사령관)

| 항목 | 상세 |
|------|------|
| **역할** | 사용자 요청 분석, 분석 계획 수립, 에이전트 할당, 최종 품질 검증 |
| **LLM** | Claude Opus 4.6 (복잡한 추론 & 계획 수립) |
| **입력** | 사용자 자연어 쿼리, 사용자 프로필 (PersonalMemory) |
| **출력** | 분석 계획 (DAG), 에이전트 할당 명세, 최종 승인/반려 |
| **특이사항** | 가장 비싼 모델이므로 호출 최소화 — 계획 수립 1회 + 최종 검증 1회 |

**의사결정 흐름:**

```
사용자: "강남역 근처에서 퓨전 한식당 열면 어떨까요?"
                    ↓
Commander 분석:
  - 의도: 특정 위치 + 특정 업종의 창업 적합도 분석
  - 필요 에이전트: 인구, 매출, 경쟁, 입지, 재무, 트렌드
  - 병렬 실행 가능: [인구, 경쟁, 트렌드] → 순차: [매출(인구 결과 필요)] → [재무] → [입지 종합]
  - 교차 검증 필요: 매출 추정치, 입지 적합도
                    ↓
실행 계획 (DAG) 생성 → LangGraph로 전달
```

### 3-2. 전문 에이전트 (Specialist Agents) 상세

#### 📊 인구분석 Agent (Population Analyst)

| 항목 | 상세 |
|------|------|
| **역할** | 상권 내 유동인구·거주인구·직장인구의 규모, 패턴, 트렌드 분석 |
| **LLM** | Gemini 2.5 Flash (빠른 데이터 해석) |
| **도구(MCP)** | 공공데이터 MCP (소상공인진흥공단 상권정보, 통계청 인구데이터) |
| **입력** | 위치 좌표/주소, 반경(500m/1km), 분석 기간 |
| **출력 스키마** | |

```
PopulationAnalysis {
    total_floating_population: int          # 일평균 유동인구
    floating_by_time: Dict[str, int]        # 시간대별 유동인구 {09시: 1200, ...}
    floating_by_day: Dict[str, int]         # 요일별 유동인구
    resident_population: int                # 반경 내 거주인구
    worker_population: int                  # 반경 내 직장인구
    age_distribution: Dict[str, float]      # 연령대별 비율
    gender_ratio: Dict[str, float]          # 성별 비율
    population_trend: str                   # "increasing" | "stable" | "decreasing"
    trend_rate: float                       # 전년 대비 증감률 (%)
    peak_times: List[str]                   # 피크 시간대 목록
    key_insight: str                        # 핵심 인사이트 (1-2문장)
    confidence_score: float                 # 데이터 신뢰도 (0~1)
    data_freshness: str                     # 데이터 최신성 (e.g., "2025-Q4")
}
```

#### 💰 매출분석 Agent (Revenue Analyst)

| 항목 | 상세 |
|------|------|
| **역할** | 해당 상권의 업종별 매출 규모, 트렌드, 계절성, 객단가 분석 |
| **LLM** | Gemini 2.5 Flash |
| **도구(MCP)** | 공공데이터 MCP (카드 매출 데이터, 국세청 업종별 매출) |
| **의존성** | 인구분석 결과 (매출 추정의 기반) |
| **출력 스키마** | |

```
RevenueAnalysis {
    area_total_revenue: int                 # 상권 전체 월평균 매출
    target_industry_revenue: int            # 목표 업종 월평균 매출
    revenue_per_store: int                  # 점포당 월평균 매출
    revenue_trend: str                      # 매출 추세
    seasonal_pattern: Dict[str, float]      # 월별 매출 지수 (1월=1.0 기준)
    avg_ticket_price: int                   # 평균 객단가
    estimated_monthly_revenue: int          # 예상 월매출 (신규 진입 시)
    revenue_range: Tuple[int, int]          # 매출 예상 범위 (하한, 상한)
    top_performing_industries: List[Dict]   # 고매출 업종 순위
    key_insight: str
    confidence_score: float
}
```

#### ⚔️ 경쟁분석 Agent (Competition Analyst)

| 항목 | 상세 |
|------|------|
| **역할** | 경쟁업체 현황, 포화도, 폐업률, 차별화 기회 분석 |
| **LLM** | Gemini 2.5 Flash |
| **도구(MCP)** | 공공데이터 MCP (사업자등록 현황), 지도 MCP (네이버/카카오 플레이스), 뉴스 MCP |
| **출력 스키마** | |

```

Phase 3: 교차 검증 Debate (2~3 라운드)
─────────────────────────────────────────

  Round 1:
  ┌──────────────────────────────────────────────┐
  │ 🗡️ Advocate (Gemini 2.5 Pro)                 │
  │ "매출 데이터와 인구 트렌드를 보면 이 상권은    │
  │  향후 2년간 성장할 가능성이 높습니다.           │
  │  근거: 유동인구 YoY +15%, 경쟁 포화도 0.4..."  │
  └──────────────────────────────────────────────┘
                        ↓
  ┌──────────────────────────────────────────────┐
  │ 🛡️ Critic (Claude Sonnet 4.6)                │

  │  공사 종료 후 급감할 수 있습니다.               │
  │  또한 폐업률 18%를 간과하고 있습니다.           │
  │  근거: 주변 재개발 일정 2026-Q3 완료 예정..."   │
  └──────────────────────────────────────────────┘

  Round 2:
```

### 5-2. Debate 트리거 조건

모든 분석에 Debate를 돌리면 비용이 과다하므로 **선택적 트리거**:

| 조건 | Debate 여부 | 이유 |
|------|------------|------|
| 에이전트 간 결론 충돌 | **필수** | 인구는 유망이라는데 경쟁은 포화라고 할 때 |
| 신뢰도 점수 < 0.6 | **필수** | 데이터 부족이나 이상 패턴 감지 시 |
| 예상 매출 변동 범위 > 50% | **필수** | 불확실성이 클 때 |
| 모든 에이전트 결론 일치 | 스킵 가능 | 불필요한 Debate 비용 절감 |
| 사용자 명시적 요청 | **필수** | "좀 더 꼼꼼히 봐줘" |

### 5-3. LLM 모델 배치 전략

| 역할 | 모델 | 선택 이유 | 호출 빈도 |
|------|------|----------|----------|
| Commander / Judge | Claude Opus 4.6 | 최고 추론 능력, 복잡한 판단 | 분석당 2회 (계획+판정) |
| Critic, 입지, 재무, 리스크, 규제, 내러티브 | Claude Sonnet 4.6 | 비판적 사고, 정밀 계산, 한국어 품질 | 분석당 3~6회 |
| Advocate, 데이터 해석, 시각화 | Gemini 2.5 Flash/Pro | 빠른 속도, 대량 데이터 처리, 웹 검색 | 분석당 5~8회 |
| 임베딩 | bge-m3 (다국어) | 한국어 상권 용어 임베딩 품질 | 상시 |

**예상 비용 (분석 1건당):**

```

Critic (Sonnet) ×3: (입력 3K + 출력 1.5K) × 3 = ~$0.058
Advocate (Gemini) ×3: ~$0.015
Specialist ×8:      ~$0.12
────────────────────────────────────
총 예상: ~$0.40~0.60 / 분석 1건
```

### 7-2. MCP 호출 흐름

```
에이전트 → MCP Client (표준 프로토콜)
              ↓
       MCP Server (Tool 실행)
              ↓
       외부 API / DB 호출
              ↓
       응답 정규화 → JSON Schema
              ↓
       에이전트에 반환
```

MCP의 이점:
- 에이전트가 데이터 소스의 구현 세부사항을 모름 (추상화)
- API 키 관리, Rate Limiting, 캐싱이 MCP 서버에서 통합 관리
- 새 데이터 소스 추가 시 에이전트 코드 변경 불필요
- 도구 목록이 자동으로 LLM에 노출 (Tool Discovery)

## 9. 기술 스택

### 9-1. 백엔드

| 구분 | 기술 | 선택 이유 |
|------|------|----------|
| **Framework** | FastAPI (Python 3.12) | async 지원, 에이전트와 동일 언어 |
| **Agent 오케스트레이션** | LangGraph | DAG 기반 워크플로우, 상태 관리, 체크포인팅 |
| **LLM 라우팅** | LiteLLM | 멀티 LLM (Claude, Gemini, GPT) 단일 인터페이스 |
| **MCP 프레임워크** | mcp-python-sdk | 공식 MCP SDK |
| **벡터 스토어** | ChromaDB | 경량, 영속, ReMe와 호환 |
| **Knowledge Graph** | LightRAG | 기존 side 프로젝트와 동일 |
| **메모리** | ReMe | 기존 side 프로젝트와 동일 |
| **RDB** | PostgreSQL + PostGIS | 공간 쿼리 지원 |
| **캐시** | Redis | API 응답 캐시, Rate Limiting |
| **태스크 큐** | Celery + Redis | 장시간 분석의 비동기 처리 |
| **스케줄러** | APScheduler | 데이터 수집 주기 실행 |

### 9-2. 프론트엔드

| 구분 | 기술 | 선택 이유 |
|------|------|----------|
| **Framework** | Next.js 15 (App Router) | SSR, 스트리밍, React Server Components |
| **UI** | shadcn/ui + Tailwind CSS | 빠른 UI 구축, 일관된 디자인 |
| **차트** | Plotly.js | 인터랙티브 차트, 다양한 차트 유형 |
| **지도** | Mapbox GL JS 또는 Kakao Maps SDK | 상권 시각화 |
| **실시간 통신** | Server-Sent Events (SSE) | 분석 진행 상황 스트리밍 |
| **상태 관리** | Zustand | 경량 상태 관리 |

### 9-3. 인프라

| 구분 | 기술 | 선택 이유 |
|------|------|----------|
| **컨테이너** | Docker + Docker Compose | 로컬 개발 & 배포 일관성 |
| **클라우드** | GCP (Cloud Run + Cloud SQL) | 초기 비용 최적화, 자동 스케일링 |
| **CI/CD** | GitHub Actions | 자동 테스트 + 배포 파이프라인 |
| **모니터링** | Langfuse | LLM 호출 추적, 비용 모니터링, 품질 평가 |
| **로깅** | Structured Logging → Loki | 에이전트별 실행 로그 추적 |

## 부록 A: 에이전트 시스템 프롬프트 가이드라인

각 에이전트의 시스템 프롬프트에 반드시 포함할 요소:

```
1. 역할 정의: "당신은 [역할]을 담당하는 전문 분석가입니다."
2. 출력 형식: "반드시 지정된 JSON 스키마에 맞춰 응답하세요."
3. 데이터 우선: "추측하지 마세요. 데이터가 없으면 'data_unavailable'로 표시하세요."
4. 신뢰도 기준: "confidence_score는 사용 가능한 데이터의 품질과 양에 따라 산정하세요."
5. 교훈 참조: "제공된 [Previous Lessons]가 현재 분석에 적용 가능한지 먼저 판단하세요."
6. 한계 인정: "확실하지 않은 분석에는 반드시 '추가 조사 권장' 태그를 붙이세요."
```
